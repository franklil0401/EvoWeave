# EvoWeave 基准评测说明

> 当前任务集版本：`evoweave_v2` v4
> 当前证据状态：第一版九组 108 条正式结果已冻结且结论为 `no_go`；第二版视觉输入和 36 条规划审计已完成，等待真实模型结果

## 1. 评测问题

评测不只回答“系统能不能运行”，而要分别回答：

1. 动态 Agent 是否比单 Agent、固定四步多 Agent 更有效；
2. 动态选模是否比固定低档或固定高档模型更合适；
3. 动态方案是否减少无效实例、冲突、总调度上下文和不必要的图片暴露；
4. 动态方案在哪些任务上没有收益或会失败。

## 2. 冻结任务集

`任务集/第二版任务集.json` 固定 12 个任务，覆盖单文件、单模块、串行多模块、并行多模块、低定位置信度、基线失败、写冲突、高风险、两个图片相关任务、图片负例和模型回退。`第一版任务集.json` 只用于重现历史 108 条结果，不再作为新运行默认输入。

每项任务固定以下信息：

- fixture 内容 SHA-256 和确定性 Git commit；
- 用户目标、验收条件和允许/禁止路径；
- 图片内容 SHA-256、MIME 和任务是否实际需要图片；
- 图片必须通过安全解码、MIME、单帧、像素上限和最小 14×14 边长校验；
- 人工难度、所需模态、人工标注修改点和回归命令；
- 基线通过或失败状态和场景标签。
- 独立隐藏验收脚本及其内容 SHA-256。

任务集文件本身也计算 SHA-256。修改任何标签、需求或路径都会得到新摘要，旧结果不能与新任务集混用。

## 3. 对照矩阵

Agent 策略：

- `single_agent`：一个通用实例负责全部授权写范围；
- `fixed_multi_agent`：固定四个串行通用实例，执行探索、实现、审查、验证步骤；
- `adaptive_agent`：按写范围、代码规模、模块依赖、风险和图片相关性生成任务图。

模型策略：

- `fixed_low`：使用一个满足硬约束的固定低档候选；
- `fixed_high`：使用一个满足硬约束的固定高档候选；
- `adaptive_model`：根据难度、模态、上下文、工具和结构化输出要求路由。

完整效果矩阵在同一真实性等级下包含 `12 × 3 × 3 = 108` 条唯一运行记录。缺少任一组合时，报告保持 `PENDING`，不得把缺失数据填成零。

## 4. 真实性等级

| 等级 | 含义 | 可以支持的结论 |
|---|---|---|
| `offline_replay` | 脚本化模型或历史响应的确定性重放 | 协议、计量和报告逻辑正确 |
| `live_model` | 锁定模型 ID、参数和能力快照的真实 API 调用 | 当前模型快照下的实际效果 |
| 规划审计 | 不调用模型，只运行真实仓库画像与任务规划器 | Agent 数、DAG、难度、风险和图片暴露 |

规划审计不属于成功率实验，离线重放也不能冒充真实模型结论。

## 5. 当前可复现命令

```powershell
uv run --no-editable evoweave benchmark validate `
  --suite benchmarks/任务集/第二版任务集.json `
  --project-root .

uv run --no-editable evoweave benchmark audit `
  --suite benchmarks/任务集/第二版任务集.json `
  --project-root . `
  --output benchmarks/结果/第二版

uv run --no-editable evoweave benchmark summarize `
  --suite benchmarks/任务集/第二版任务集.json `
  --results benchmarks/结果/第二版/真实模型结果.json `
  --output benchmarks/结果/第二版

uv run --no-editable evoweave benchmark run `
  --suite benchmarks/任务集/第二版任务集.json `
  --project-root . `
  --results benchmarks/结果/第二版/真实模型结果.json
```

`validate` 校验 fixture、commit、图片摘要、图片实际格式与尺寸，以及隐藏验收摘要；`audit` 产生规划审计；`run` 调用当前账号已发现的真实模型并逐条原子保存结果与证据；`summarize` 只聚合已有运行记录。第一版 108 条历史结果已经覆盖全部九个组合；第二版尚未完成完整矩阵，因此新报告必须保持 `PENDING`。

## 6. 指标与防作弊规则

核心指标包括任务成功率、定位召回率、补丁有效率、回归率、总 Token、墙钟时延、Agent 数、无效任务率、冲突率、总调度/Worker 上下文量、首次路由有效率、回退率、难度匹配率和图片暴露数。

第二版把“模型硬约束合规率”和“首次执行成功率”分为两个字段，并为每个策略组合记录 `trial_index`。同一重复内必须覆盖全部 12 个任务，九个策略组合必须具有相同且完整的重复集合；否则 Go/No-Go 保持 `PENDING`。报告同时输出跨次成功率、平均 Token 和平均时延的总体标准差，单次运行标准差记为 0 但不能解释为稳定。

评测必须遵守：

- 三种策略使用同一个任务 commit、允许路径、运行上限和确定性验收；
- 目标测试与全量回归同时通过才算任务成功；
- 补丁越权、未应用或未授权不能记为通过；
- 运行失败必须记录结构化原因，不能删除失败样本；
- 同一报告中的记录必须绑定同一个任务集 SHA-256 和同一个系统 Git commit；
- 不按费用或预算选择模型；
- API Key 值、完整私有推理和未脱敏源码不得进入结果文件；
- 每项隐藏验收都必须证明原始基线失败、已知正确实现通过；fixture 自带 Pytest 只承担回归检查，不能替代需求验收。
- 模型回退场景必须注入一次可审计的首选模型不可用故障，并验证新版 Agent/执行规格和路由确实产生；图片正例/负例同时接受系统级原图暴露检查。

## 7. 当前结果

[规划审计报告](结果/规划审计报告.md)已经完成 36 条规划记录。动态策略的冻结人工难度匹配为 12/12；平均创建 1.33 个实例；两个图片相关任务共向 2 个动态 Agent 暴露原图；图片负例暴露为 0。

这些数字只描述规划行为。第二版任务集曾执行 12 条动态策略真实调用，其中 4 条通过；随后发现任务 11 的隐藏验收错误导入了其他 fixture 的模块。第三版在系统提交 `4a9b867` 上又完成 12 条探索运行，其中 5 条通过，但任务 12 没有实际触发模型回退，运行器却只按最终代码判为通过，暴露了系统级验收缺口。两轮记录、汇总和证据均完整移入 `结果/已废弃/`，不能作为正式成功率。

补齐故障注入和系统级验收后，提交 `10385091b453b4753f1a84a9b56388fb26a049ca` 上已完成动态 Agent + 动态模型的 12 条正式 `live_model` 运行：6 条通过，成功率 50.0%，平均 Token 55,753.9，平均时延 152,948.6 ms，平均 Agent 数 2.42，回退率 58.3%，定位召回率 95.8%，总调度上下文占 Worker 上下文约 3.71%。模型回退任务实际创建了第 2 个 Agent并切换供应商；两个图片正例只向视觉 Agent 暴露原图，但旧任务集图片只有 4×4 像素，低于厂商接口限制，因此失败；图片负例保持 0 个图片 Agent并通过。复杂串行/并行任务的主要失败原因是模型在结构化决策 JSON 后附加额外内容，高风险任务则因新增回归被门禁拒绝。

同一提交上的单 Agent + 固定低档模型组已完成 12 条正式运行：0 条通过，平均 Token 85,619.3，平均时延 61,584.2 ms。9 个文本任务达到确定性运行上限，2 个图片任务因模型服务不可用失败，模型回退任务按固定策略在注入故障后直接失败。该组说明固定低档候选不适合当前完整代码工具循环，但还不能替代其他 Agent/模型组合的对照。

单 Agent + 固定高档模型组也已完成 12 条正式运行：6 条通过，成功率与动态组同为 50.0%，平均 Token 27,128.0，平均时延 27,995.8 ms，分别为动态组的约 48.7% 和 18.3%。它在单模块和并行任务上快速通过，但仍在结构化输出、高风险验收、无效图片输入和故障注入后无回退场景失败。当前数据未证明动态组优于强单 Agent，必须继续完成其余策略组合。

单 Agent + 动态模型组完成 12 条正式运行：7 条通过，成功率 58.3%，平均 Token 43,283.7，平均时延 71,440.8 ms，平均执行实例 1.83 个。任务规划始终为单节点，但模型失败会按系统规则创建新版 Agent 和路由，因此执行实例可多于一个。该组在串行和并行多模块任务上通过，当前成功率高于动态 Agent + 动态模型组，且 Token、时延更低；现有证据更支持动态选模的价值，尚未支持动态增加任务节点。

动态 Agent + 固定高档模型组完成 12 条正式运行：4 条通过，成功率 33.3%，平均 Token 19,864.5，平均时延 29,876.8 ms，平均执行实例 1.17 个。较低用量主要来自多个任务提前因结构化协议失败，不能解释为效率优势。该组低于固定高档单 Agent的 6/12；模型能力相同后，额外任务节点增加了模型决策次数，并放大输出不稳定。

动态 Agent + 固定低档模型组完成 12 条正式运行：1 条通过，成功率 8.3%，平均 Token 68,375.4，平均时延 55,862.7 ms，平均执行实例 1.08 个。除一个低置信度任务外，大部分文本任务达到运行上限；并行任务虽启动 2 个 Agent，但两者都未收敛。动态拆分无法稳定补偿弱模型能力。

固定多 Agent + 固定高档模型组完成 12 条正式运行：0 条通过，平均 Token 75,095.3，平均时延 78,668.8 ms，平均执行实例 2.67 个。7 个任务因 Worker 决策协议无效失败，2 个图片任务因 4×4 输入被接口拒绝；故障注入任务按固定模型策略不回退。与同模型单 Agent的 6/12 相比，固定四步流水线没有带来收益，反而显著增加结构化调用失败面。

固定多 Agent + 动态模型组完成 12 条正式运行：0 条通过，平均 Token 129,826.1，平均时延 188,675.5 ms，平均执行实例 3.92 个，总计 6 次模型回退。3 个任务达到确定性运行上限；其余失败来自结构化协议、隐藏验收、全量回归、需求未实现和无效图片输入。动态候选增加了恢复尝试，但在固定四步拓扑中没有转化为成功，并显著扩大 Token 和时延。

固定多 Agent + 固定低档模型组完成 12 条正式运行：3 条通过，成功率 25.0%，平均 Token 90,490.8，平均时延 68,374.5 ms，平均执行实例 2.33 个。低置信度、写冲突和图片负例任务通过；5 个任务达到运行上限，2 个图片正例因 4×4 输入被接口拒绝，故障注入任务按固定策略不回退。该组高于另两个固定多 Agent组，但仍明显低于最佳单 Agent + 动态模型的 58.3%。

[正式评测汇总报告](结果/评测汇总报告.md)展示全部 108 条第一版结果，自动结论为 `no_go`。简单任务最小实例与总调度上下文压缩门槛通过，动态方案相对最佳基线的性能门槛未通过；第一版报告把 `initial_route_success_rate` 作为“模型硬约束”门槛的口径缺陷已在代码中修复，但第一版文件保持原样。第二版必须在新系统提交和独立目录中重新生成报告，不能用新代码重写旧结论。

## 8. 第二版执行约束

- 第二版结果必须写入独立目录，不能追加到 `结果/真实模型结果.json`；
- 首轮真实复测优先运行 `adaptive_agent + adaptive_model` 与最佳基线 `single_agent + adaptive_model`，用于验证修复方向；完整 Go/No-Go 仍要求九组和相同重复集合；
- 推荐至少 3 次重复，使用 `benchmark run --trials 3` 原子续跑；视觉输入必须先通过本地尺寸校验和至少两家供应商的独立连通探测，不把输入缺陷解释为拓扑或服务失败。
