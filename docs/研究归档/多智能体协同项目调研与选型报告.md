# 多 Agent 协同项目调研与选型报告

> 面向秋招项目准备
>
> 调研时间：2026-08-12
>
> 重点项目：MetaGPT

## 1. 结论摘要

MetaGPT 是目前最值得深入阅读的多 Agent 协作项目之一。它把“软件公司”的组织结构抽象成多个 LLM Agent，并通过标准作业流程（SOP）、消息路由、角色记忆和文档依赖来完成软件开发任务。

它最有价值的地方不是“让几个 Agent 聊天”，而是把协作过程结构化：

```text
用户需求
   ↓
Team / Environment
   ↓ 消息路由
Product Manager → Architect → Project Manager → Engineer → QA Engineer
   ↓
PRD、系统设计、任务列表、代码、测试和审查结果
```

对于秋招，不建议直接把 MetaGPT 仓库改名后作为自己的项目。更好的方式是：

1. 阅读 MetaGPT，理解 Role、Action、Message、Environment、Team 和 SOP。
2. 选择一个明确的业务场景，重新设计 Agent 角色和协作协议。
3. 使用 LangGraph 或 CrewAI 实现较小而清晰的系统，或基于 MetaGPT 编写独立扩展。
4. 加入结构化输出、失败重试、人工确认、日志追踪和评测指标。

最终推荐项目方向：

> **基于多 Agent 协同的软件研发助手**
>
> 输入自然语言需求，由需求分析 Agent、架构设计 Agent、编码 Agent、测试 Agent 和代码审查 Agent 协同完成需求拆解、代码生成、测试和质量反馈。

这个方向与 MetaGPT 的核心思想一致，但可以体现你自己的工程设计，而不是简单复现官方 Demo。

## 2. MetaGPT 项目概况

项目地址：[FoundationAgents/MetaGPT](https://github.com/FoundationAgents/MetaGPT)

MetaGPT 官方将项目定位为“Software Company as Multi-Agent System”，即把软件公司中的产品经理、架构师、工程师和测试人员抽象成 Agent。项目的核心理念是：

```text
Code = SOP(Team)
```

也就是：代码产出来自团队协作流程，而不是单个 Agent 的一次性生成。

官方 README 描述的基本流程是：输入一行需求，系统输出用户故事、竞争分析、需求文档、数据结构、API、代码和其他项目文件。官方仓库采用 Python 实现，当前 README 要求 Python 3.9 及以上且低于 3.12，并且部分功能需要 Node.js 和 pnpm。

项目许可证为 MIT，仓库规模较大，包含 `metagpt` 核心库、`examples`、`tests`、配置和文档等目录。建议学习时固定一个 commit 或 release，避免因主分支 API 变化导致复现困难。

## 3. MetaGPT 源码结构

核心目录位于 [`metagpt/`](https://github.com/FoundationAgents/MetaGPT/tree/main/metagpt)：

| 目录或文件 | 作用 |
|---|---|
| `metagpt/roles/` | Agent 角色定义，如产品经理、架构师、工程师、测试工程师 |
| `metagpt/actions/` | Agent 能执行的原子动作，如写 PRD、设计 API、写代码、写测试 |
| `metagpt/environment/` | Agent 所处的协作环境、消息发布和路由 |
| `metagpt/team.py` | 团队生命周期、角色雇佣、预算、项目启动和运行轮次 |
| `metagpt/schema.py` | Message、Document、Task 等数据结构 |
| `metagpt/memory/` | Agent 记忆和历史记录 |
| `metagpt/document_store/` | 需求、设计、任务、代码等文档的保存和管理 |
| `metagpt/tools/` | 浏览器、编辑器、终端等工具 |
| `metagpt/strategy/` | 计划和执行策略 |
| `metagpt/software_company.py` | 默认软件公司流程的启动入口 |
| `examples/` | 自定义 Agent、Data Interpreter 和应用示例 |

建议阅读顺序：

1. `examples/build_customized_multi_agents.py`
2. `metagpt/roles/role.py`
3. `metagpt/actions/action.py`
4. `metagpt/schema.py`
5. `metagpt/environment/base_env.py`
6. `metagpt/team.py`
7. `metagpt/software_company.py`
8. 具体角色和动作，例如 `product_manager.py`、`architect.py`、`engineer.py`、`qa_engineer.py`

## 4. MetaGPT 的核心抽象

### 4.1 Role：Agent 的角色和运行循环

源码入口：[metagpt/roles/role.py](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/roles/role.py)

`Role` 是 MetaGPT 中最核心的 Agent 抽象。一个 Role 通常包含：

- `name`：角色名称
- `profile`：角色身份，例如 Product Manager、Architect
- `goal`：角色目标
- `constraints`：角色约束
- `actions`：该角色可以执行的动作
- `memory`：角色记忆
- `watch`：该角色关注哪些类型的消息
- `state`：当前动作状态
- `react_mode`：如何选择和执行动作

Role 的典型运行过程是：

```text
run()
 ├─ _observe() 读取消息缓冲区并过滤自己关注的消息
 ├─ _think()   选择下一步 Action
 ├─ _act()     调用 Action 并生成结果
 ├─ 记忆结果
 └─ publish_message() 将结果发送给其他 Role
```

MetaGPT 当前实现提供三种主要反应模式：

| 模式 | 含义 |
|---|---|
| `react` | LLM 在每轮动态选择下一个 Action，形成 Think-Act 循环 |
| `by_order` | 按照预先定义的 Action 顺序执行，适合固定 SOP |
| `plan_and_act` | 先生成计划，再按照计划逐项执行 |

这部分很适合你在面试中讲解，因为它体现了 Agent 的状态管理，而不仅是调用一次大模型。

### 4.2 Action：可复用的工作单元

源码入口：[metagpt/actions/action.py](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/actions/action.py)

Action 是一个具体工作单元，例如：

- `WritePRD`：生成产品需求文档
- `WriteDesign`：生成系统设计
- `WriteTasks`：拆解开发任务
- `WriteCode`：编写代码
- `WriteCodeReview`：代码审查
- `WriteTest`：生成测试
- `FixBug`：修复问题

Role 负责决定“谁来做”和“什么时候做”，Action 负责“具体做什么”。这种拆分带来两个优点：

1. 相同的 Action 可以被多个 Agent 复用。
2. Agent 的协作逻辑和具体任务逻辑可以独立演进。

### 4.3 Message：Agent 之间的协作协议

源码入口：[metagpt/schema.py](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/schema.py)

MetaGPT 的 Message 不只是一个字符串，主要字段包括：

| 字段 | 作用 |
|---|---|
| `content` | 自然语言内容 |
| `instruct_content` | 结构化输出，例如 Pydantic 模型 |
| `cause_by` | 这条消息由哪个 Action 产生 |
| `sent_from` | 消息发送者 |
| `send_to` | 消息接收者 |
| `metadata` | 额外的上下文信息 |

`cause_by` 和 `send_to` 是 MetaGPT 协作机制的关键。Agent 可以根据消息来源决定是否响应，也可以将消息定向发送给某个角色。

例如：

```text
WritePRD 产生 PRD 消息
        ↓
Architect 监听 WritePRD
        ↓
WriteDesign 产生系统设计消息
        ↓
Engineer 监听 WriteTasks / WriteDesign
        ↓
WriteCode 产生代码消息
```

### 4.4 Environment：消息总线和协作空间

源码入口：[metagpt/environment/base_env.py](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/environment/base_env.py)

`Environment` 保存一批 Role，并负责：

- 注册 Role
- 管理 Role 地址
- 接收和分发消息
- 保存全局消息历史
- 并发运行处于非空闲状态的 Role
- 判断整个团队是否完成任务

当前实现通过 `asyncio.gather` 并发运行多个 Role。这种设计意味着多个 Agent 可以在同一轮中并行处理各自已有的消息，从而降低等待时间。

但它不是完全独立进程的分布式 Agent 系统。默认情况下，各 Role 仍然运行在同一个 Python 进程中；如果要做到真正的服务化、隔离和弹性调度，需要额外增加任务队列、数据库、服务注册和执行沙箱。

### 4.5 Team：团队生命周期和预算控制

源码入口：[metagpt/team.py](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/team.py)

`Team` 负责：

- `hire()`：加入多个 Role
- `invest()`：设置预算
- `run_project()`：发布用户需求
- `run()`：按轮次推进整个团队
- `serialize()` / `deserialize()`：保存和恢复团队状态

MetaGPT 将模型调用成本纳入预算管理。当总成本达到预算时，团队会停止运行。这一点是普通 Demo 中经常缺少的工程能力，非常适合迁移到自己的项目中。

### 4.6 文档和代码依赖

MetaGPT 不是简单地让 Agent 通过长对话传递所有上下文，而是会把需求、设计、任务、代码和总结保存为项目文档，并维护它们之间的依赖关系。

这带来一个重要启发：

> 多 Agent 之间应该传递结构化的中间产物，而不是无边界地共享全部聊天记录。

在你自己的项目中，建议让每个 Agent 输出 Pydantic 模型或 JSON，例如：

```python
class RequirementSpec(BaseModel):
    goal: str
    users: list[str]
    functions: list[str]
    constraints: list[str]
    acceptance_criteria: list[str]
```

这样可以降低上下文长度，减少 Agent 之间的歧义，也方便测试和评测。

## 5. MetaGPT 默认软件研发流程

官方启动入口：[metagpt/software_company.py](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/software_company.py)

当前主流程会组建包含 Team Leader、Product Manager、Architect、Engineer 和 Data Analyst 等角色的团队。不同版本或配置可能启用 Project Manager、QA Engineer、代码审查等角色，因此实际运行时应以固定版本源码为准。

可以将其概括为：

```text
用户需求
  ↓
Team Leader / Product Manager
  ├─ 需求分析
  ├─ PRD
  └─ 市场或竞品信息
  ↓
Architect
  └─ 系统设计、API 和技术方案
  ↓
Project Manager
  └─ 任务拆解和依赖管理
  ↓
Engineer
  ├─ 代码生成
  ├─ 代码总结
  └─ 失败后重新编码
  ↓
QA Engineer / Reviewer
  ├─ 生成测试
  ├─ 执行测试
  └─ 反馈缺陷
```

工程师角色的源码还体现了一个重要机制：代码生成后先总结或审查，如果检查不通过，则把问题转化成新的任务，再重新进入编码流程。这个“失败反馈闭环”比“一次生成代码”更适合作为秋招项目的技术亮点。

## 6. 官方自定义多 Agent 示例

示例文件：[examples/build_customized_multi_agents.py](https://github.com/FoundationAgents/MetaGPT/blob/main/examples/build_customized_multi_agents.py)

官方示例定义了三个简单角色：

| Agent | 任务 |
|---|---|
| `SimpleCoder` | 根据用户需求写 Python 函数 |
| `SimpleTester` | 根据代码生成 pytest 测试 |
| `SimpleReviewer` | 审查测试并提出改进建议 |

示例中，Tester 监听 `SimpleWriteCode` 产生的消息，Reviewer 监听 `SimpleWriteTest` 产生的消息。也就是说，角色之间不是硬编码的函数调用，而是通过消息的 `cause_by` 和订阅关系进行协作。

运行逻辑可以概括为：

```python
team = Team()
team.hire([SimpleCoder(), SimpleTester(), SimpleReviewer()])
team.invest(investment=3.0)
team.run_project(idea)
await team.run(n_round=5)
```

这是非常适合作为第一阶段练习的最小闭环。建议先将它改成：

```text
需求分析 Agent → 代码设计 Agent → 编码 Agent → 测试 Agent → 审查 Agent
```

再逐步加入工具、数据库和 Web 界面。

## 7. MetaGPT 的优点和不足

### 优点

- 角色、动作和协作流程的抽象清晰。
- 使用消息来源和接收者实现可解释的路由。
- 支持固定 SOP、ReAct 和 Plan-and-Act 等不同执行方式。
- 有记忆、文档、项目仓库、成本控制和状态恢复机制。
- 适合展示多 Agent 协作，而不是只展示单 Agent 工具调用。
- 有软件研发、数据分析、浏览器和工具使用等多个示例。

### 不足

- 代码规模较大，直接阅读全部仓库成本高。
- 依赖较多，安装时可能涉及 Python、Node.js、pnpm、Docker 和外部模型服务。
- 大模型输出不稳定，Role 的状态选择、消息路由和结构化输出都可能失败。
- Agent 数量增加后，Token 成本、延迟和上下文管理压力明显上升。
- 默认代码执行、终端和浏览器工具存在安全风险，不能直接暴露到公网。
- 直接复现“输入一句话生成软件”的 Demo，容易变成缺少原创性的套壳项目。
- 主分支持续演进，学习和部署时需要固定版本并记录环境。

## 8. 其他值得研究的多 Agent Python 项目

### 8.1 CrewAI

项目地址：[crewAIInc/crewAI](https://github.com/crewAIInc/crewAI)

CrewAI 是更容易上手的 Python 多 Agent 框架，核心概念是：

- **Crews**：多个具有角色、目标和工具的 Agent 自主协作。
- **Flows**：事件驱动、可控、适合生产场景的工作流。

官方文档强调 Agent 可以执行任务、使用工具、维护记忆、委派任务并与其他 Agent 协作。

适合：

- 快速做出一个可以运行的多 Agent 应用。
- 研究员、写作者、审查员、总结员等角色协作。
- 需要较少框架源码阅读量的项目。

不适合：

- 想深入研究底层消息总线和复杂状态机。
- 想完全自定义每一个调度细节。

秋招评价：上手难度低，Demo 效果好，但由于使用者较多，必须加入评测、工具、异常处理和工程化能力，才能避免“只会调用 CrewAI”的印象。

### 8.2 CAMEL-AI

项目地址：[camel-ai/camel](https://github.com/camel-ai/camel)

CAMEL 更偏向多 Agent 研究、Agent Society 和大规模 Agent 行为探索。官方组件包括：

- Agents
- Agent Societies
- Tools
- Memory
- Storage
- Benchmarks
- Retrievers / RAG
- Runtime
- Human-in-the-Loop

CAMEL 适合做：

- 多 Agent 角色扮演和协商。
- 多 Agent 研究助手。
- 数据生成和合成数据实验。
- Agent 社会模拟。
- 带评测的 Agent 研究项目。

秋招评价：研究味道更强，适合算法、NLP、Agent Research 方向；如果目标是快速交付一个业务系统，学习成本通常高于 CrewAI。

### 8.3 AG2 / AutoGen 生态

项目地址：[ag2ai/ag2](https://github.com/ag2ai/ag2)

AG2 是 AutoGen 生态的后续项目，提供多 Agent 协作、工具调用、人工介入、网络式编排和 Agent 间通信能力。

需要特别注意版本变化：AG2 v1.0 使用 `import ag2`，而旧式 `autogen.*` 经典 API 已被拆分到 [ag2ai/ag2-classic](https://github.com/ag2ai/ag2-classic)。两者的 Agent 模型、导入方式和编排方式并不完全兼容。

适合：

- 研究群聊、嵌套对话和 Agent handoff。
- 需要人工参与的多 Agent 流程。
- 研究不同协作拓扑和通信协议。

秋招评价：概念经典，面试辨识度高；但必须提前锁定版本，不能混用 AutoGen、AG2 Classic 和 AG2 v1.0 的代码。

另外，微软原始的 [microsoft/autogen](https://github.com/microsoft/autogen) 官方 README 目前提示其进入维护模式，新项目应谨慎直接使用原仓库作为长期底座。

### 8.4 AgentVerse

项目地址：[OpenBMB/AgentVerse](https://github.com/OpenBMB/AgentVerse)

AgentVerse 主要提供两个方向：

1. Task-solving：多个 Agent 共同解决任务。
2. Simulation：多个 Agent 在环境中进行交互和社会模拟。

官方示例包括课堂场景模拟，一个教授 Agent 与多个学生 Agent 交互；同时也支持 HumanEval、工具使用和本地模型配置。

适合：

- 多 Agent 社会模拟。
- 多角色对话行为研究。
- 研究 Agent 的协作和涌现行为。

秋招评价：研究价值较高，但仓库整体更偏论文和实验框架，工程化应用体验不如 LangGraph、CrewAI。

### 8.5 agentUniverse

项目地址：[agentuniverse-ai/agentUniverse](https://github.com/agentuniverse-ai/agentUniverse)

agentUniverse 是 Python 多 Agent 框架，提供 Agent、工具、知识库、工作流和 PEER 多 Agent 机制，适合中文企业场景和领域任务。

官方介绍中提到的 PEER 框架包含多个专家角色，并对完整性、相关性、简洁性、事实性、逻辑性、结构和全面性等维度进行评估。

适合：

- 中文 Agent 应用。
- 领域专家 Agent 协作。
- 企业知识库和流程自动化。

秋招评价：适合作为国内项目参考；不过建议先验证当前版本的文档完整度、依赖和实际运行状态，再决定是否作为项目主框架。

### 8.6 LangGraph

项目地址：[langchain-ai/langgraph](https://github.com/langchain-ai/langgraph)

LangGraph 不是一个开箱即用的“软件公司 Agent”，而是一个低层工作流和状态编排框架。它重点解决：

- 有状态 Agent。
- 持久化和故障恢复。
- 人机协同。
- 长时间运行任务。
- 分支、循环和子图。
- Agent 轨迹调试和观测。

适合：

- 自己设计协作拓扑。
- 将流程画成明确的状态图。
- 构建可恢复、可测试的 Agent 系统。

秋招评价：最适合作为自己重新实现多 Agent 项目的底座之一。它能让你清楚展示节点、状态、路由、重试、人工确认和持久化，而不是把关键逻辑隐藏在框架内部。

### 8.7 Microsoft spec-to-agents

项目地址：[microsoft/spec-to-agents](https://github.com/microsoft/spec-to-agents)

这是一个多 Agent 活动策划系统示例，使用 5 个专业 Agent：场地、预算、餐饮、物流和协调器。项目包含：

- 协调器中心的星型拓扑。
- Web 搜索、天气、日历和 Python 代码解释器工具。
- Human-in-the-Loop。
- Pydantic 结构化输出。
- 动态 Agent 路由。
- 测试和 Azure 部署。

它非常适合作为现代企业级多 Agent 项目的架构参考，但运行依赖 Azure 资源，成本和配置门槛高于本地 Python Demo。

### 8.8 Open Deep Research

项目地址：[langchain-ai/open_deep_research](https://github.com/langchain-ai/open_deep_research)

这是一个完整的深度研究 Agent 应用，支持搜索工具、MCP、多模型配置、报告生成和 Deep Research Bench 评测。它更接近“可展示的应用项目”，而不是通用多 Agent 框架。

适合：

- 研究员 Agent 并行搜索。
- 信息整合和报告生成。
- 引用溯源和事实核查。
- 评测 Agent 的研究质量。

如果把它与 MetaGPT 的角色协作结合，可以做成“研究主管—搜索员—事实核查员—报告撰写员”的多 Agent 系统。

## 10. 适合你的项目方案

### 方案 A：多智能体软件研发协同平台（首选）

项目名称可以是：

> **DevTeam Agents：基于多 Agent 协同的软件研发助手**

#### 功能流程

```text
用户输入需求
    ↓
需求分析 Agent
    ↓
架构设计 Agent
    ↓
任务规划 Agent
    ↓
编码 Agent ─────┐
    ↓           │ 失败反馈
测试 Agent ─────┘
    ↓
代码审查 Agent
    ↓
人工确认 / 输出项目报告
```

#### Agent 设计

| Agent | 输入 | 输出 |
|---|---|---|
| Requirement Agent | 用户需求 | 结构化需求、验收标准 |
| Architect Agent | 需求文档 | 模块划分、API、数据模型 |
| Planner Agent | 需求和设计 | 有依赖关系的任务列表 |
| Coder Agent | 任务、设计、代码上下文 | 代码补丁 |
| Tester Agent | 代码和验收标准 | 测试用例、执行结果 |
| Reviewer Agent | 需求、代码、测试结果 | 缺陷、风险和修改建议 |
| Coordinator Agent | 全部中间结果 | 路由、重试、最终总结 |

#### 建议实现技术

- Python 3.11
- LangGraph 或 CrewAI
- FastAPI
- Pydantic
- SQLite 或 PostgreSQL
- Redis 可选，用于任务队列和缓存
- Docker 沙箱，用于执行生成代码和测试
- Chroma / Qdrant 可选，用于项目文档检索
- Streamlit 或 React，用于展示 Agent 执行过程

#### 必须做出的差异化

- 不是只生成代码，而是生成完整的需求、设计、任务、代码和测试链路。
- 每个中间产物有结构化 Schema。
- 测试失败能够触发自动返工。
- 代码执行必须在受限沙箱中完成。
- 支持人工审批后再执行高风险操作。
- 保存完整 Agent 轨迹，能够展示每个角色为什么被调用。
- 有基础评测集，统计任务成功率、测试通过率、平均 Token、平均耗时和重试次数。

### 方案 B：多智能体智能调研系统

项目名称可以是：

> **ResearchTeam Agents：多 Agent 协同的智能调研与报告生成系统**

Agent 角色包括：

- Research Manager：拆解问题。
- Search Agent：搜索网页、论文或 GitHub。
- Extraction Agent：提取证据。
- Fact Checker：核验冲突信息。
- Analyst：归纳和比较。
- Writer：生成报告和引用。

这个方案更容易做出稳定 Demo，也更适合加入 RAG、搜索、引用和评测。如果你希望快速完成并且项目界面效果好，方案 B 的风险低于方案 A。

### 方案 C：多 Agent 求职岗位分析助手

项目名称可以是：

> **CareerCrew：多 Agent 秋招岗位分析与面试准备系统**

可以让 Agent 协作完成：

- 抓取和解析岗位描述。
- 提取岗位技术栈。
- 与用户简历匹配。
- 分析知识差距。
- 生成学习计划。
- 生成针对性面试题。
- 由审查 Agent 检查题目是否覆盖岗位要求。

这个项目与秋招主题直接相关，Demo 也容易理解，但技术问题容易被误解成简单的文本分类。需要加入检索、工具调用、结构化输出和多轮反馈，才能体现多 Agent 价值。

## 11. 推荐技术路线

### 第一阶段：理解 MetaGPT

完成官方自定义示例，并回答以下问题：

- Role 如何接收消息？
- `watch` 如何决定 Agent 是否响应？
- `cause_by` 和 `send_to` 分别解决什么问题？
- Environment 如何广播消息？
- 多个 Role 如何并发运行？
- Action 和 Role 为什么要分开？
- Team 如何管理预算和恢复状态？

### 第二阶段：实现最小协作闭环

先不要接入复杂工具，只实现：

```text
Coder → Tester → Reviewer
```

要求每个 Agent 输出结构化对象，并保存执行轨迹。

### 第三阶段：扩展为完整项目

加入需求分析、架构设计、任务规划、代码生成、测试、审查和重试，形成 5 到 7 个 Agent 的闭环。

### 第四阶段：工程化

加入：

- FastAPI API 服务。
- Web 界面。
- Docker 沙箱。
- 数据库持久化。
- 日志和 Trace。
- 超时、重试和降级。
- 人工确认节点。
- 单元测试和集成测试。

### 第五阶段：评测和简历化

至少设计 20 个固定任务，记录：

| 指标 | 说明 |
|---|---|
| 任务成功率 | 是否完成用户目标 |
| 测试通过率 | 生成代码是否通过自动测试 |
| 首次成功率 | 不重试时的完成比例 |
| 平均重试次数 | 失败反馈闭环的代价 |
| 平均延迟 | 从输入到最终结果的时间 |
| 平均 Token / 成本 | 单任务调用开销 |
| 幻觉或引用错误率 | 调研类项目需要重点统计 |
| 人工介入率 | 多少任务需要人工确认 |

## 12. 最终选型建议

### 如果重点是学习 MetaGPT

选择：**MetaGPT + 自定义 Role / Action**

适合研究其消息路由、SOP 和文档依赖，但需要固定版本并接受较高的代码复杂度。

### 如果重点是尽快做出完整 Demo

选择：**CrewAI + FastAPI + Streamlit**

角色和任务定义简单，适合先完成一个能运行的多 Agent 应用，再补充评测和工程化。

### 如果重点是展示系统设计能力

选择：**LangGraph + Pydantic + Docker 沙箱**

可以明确展示状态图、条件路由、重试、人工审批、持久化和失败恢复。

### 如果重点是研究 Agent 协作机制

选择：**CAMEL 或 AG2**

适合研究角色协商、Agent Society、群聊和不同通信拓扑，但需要投入更多时间理解框架和实验设计。

### 对你的最终推荐

建议采用下面的组合：

```text
MetaGPT：学习角色、Action、消息和 SOP 设计
LangGraph：实现可控的状态图和协作流程
Qwen / OpenAI-compatible API：提供模型能力
Pydantic：约束 Agent 中间产物
Docker：隔离代码执行
FastAPI + Streamlit：提供服务和演示界面
```

项目最终可以表述为：

> 设计并实现一个基于 LangGraph 的多智能体软件研发协同系统，参考 MetaGPT 的角色化 SOP 和消息路由机制，将需求分析、架构设计、任务拆解、代码生成、自动测试与代码审查组织为可恢复状态图；通过 Pydantic 约束 Agent 中间产物，使用 Docker 沙箱执行生成代码，并加入失败重试、人工审批、轨迹追踪和任务成功率评测。

这比直接写“使用 MetaGPT 实现了多 Agent 项目”更能体现你的独立设计和工程能力。
