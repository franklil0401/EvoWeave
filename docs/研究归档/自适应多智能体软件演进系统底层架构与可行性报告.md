# 自适应多 Agent 软件演进系统：底层架构与可行性报告

> 面向秋招项目的技术决策文档  
> 调研日期：2026-08-13  
> 目标：先证明底层方案可行，再决定是否进入编码

## 技术摘要

**项目可行，但不应直接建立在 MetaGPT 的完整运行时之上。** MetaGPT 最值得继承的是 `Role / Action / Message / Environment` 协作抽象、结构化中间产物和 SOP 思想；不适合直接继承的是固定团队入口、共享工作目录式执行、以轮次推进的调度，以及缺少强隔离的代码执行路径。

建议把系统定义为“**基于变更影响分析的自适应多 Agent 软件演进系统**”，而不是泛化的“多 Agent 操作系统”。底层采用三部分组合：

1. **单 Agent 软件工程内核**：每个 Worker 都是简单、可测、可限制的 `observe → reason → act → observe` 循环。
2. **持久化任务图控制平面**：根据需求和仓库影响范围选择有限的协作拓扑，负责暂停、恢复、重试、预算和人工审批。
3. **隔离执行平面**：每个写代码的 Worker 使用独立 Git worktree 和容器，只输出补丁；集成器串行合并，测试门禁决定是否接受。

第一版不训练 MaAS 式神经控制器，也不允许 LLM 任意发明 Agent 网络。先使用**确定性仓库特征 + LLM 结构化判断 + 有限拓扑模板**完成动态组队，并通过单 Agent、固定多 Agent、自适应多 Agent 三组实验验证收益。只有当消融实验表明动态路由确实提高成功率或降低成本，才进入学习型控制器阶段。

**Go / No-Go 结论：有条件 Go。** 在正式编写完整系统前，必须先完成三个技术尖峰（Technical Spike）：旧仓库定位与补丁闭环、双 worktree 并行与无冲突集成、同一任务的动态路由对照实验。三个尖峰全部通过后，方案才算被工程证据证明可行。

## 1. “底层”在本报告中的定义

这里的“底层”不是大模型本身，而是模型之上的 Agent 运行时。为了避免只讨论角色名称，本报告把底层拆为六层：

| 层次 | 核心问题 | MetaGPT 中的对应物 | 我们需要的对应物 |
|---|---|---|---|
| 模型适配层 | 如何调用不同 LLM、统计成本、重试 | Provider、BaseLLM、CostManager | `ModelGateway`、预算与调用日志 |
| Agent 内核层 | 一个 Agent 如何观察、思考、行动 | `Role`、`Action`、ReAct | 极简 `WorkerRuntime` |
| 状态与协议层 | Agent 如何交换可验证信息 | `Message`、`Memory`、Document | 事件日志 + Pydantic 任务/补丁协议 |
| 控制平面 | 谁运行、何时运行、失败怎么办 | `Team`、`Environment`、TeamLeader | 持久化 DAG、调度器、锁、重试、审批 |
| 代码执行平面 | 如何读写仓库和运行命令 | ProjectRepo、Editor、Terminal | worktree + 容器 + 最小权限工具 |
| 验证与安全层 | 如何证明补丁正确且不伤害宿主机 | 测试 Action、有限的预算/轮次 | 测试门禁、安全策略、回滚、审计 |

**判断一个框架能否当底座，关键不在它能否创建多个角色，而在后四层是否适合“修改真实旧仓库”这一高副作用任务。**

## 2. MetaGPT 的底层到底是什么

### 2.1 本质：以消息驱动的角色状态机执行 SOP

MetaGPT 官方把核心思想概括为 `Code = SOP(Team)`：把产品经理、架构师、工程师等角色及其标准作业流程编码为协作系统。源码中的核心对象关系如下：

```text
Team
 └─ Environment / MGXEnv
     ├─ Role A ─ Actions ─ Memory ─ MessageQueue
     ├─ Role B ─ Actions ─ Memory ─ MessageQueue
     └─ Role C ─ Actions ─ Memory ─ MessageQueue

Message(cause_by, sent_from, send_to, instruct_content)
                ↓ Environment 路由
Role.run() = observe → think → act → publish
```

`Role` 保存身份、目标、Action 列表、记忆、消息缓冲和当前状态。它支持三种行为模式：LLM 动态选择 Action 的 `react`、顺序执行的 `by_order`、先计划再执行的 `plan_and_act`。`run()` 先观察消息，再执行反应循环，最后将结果发布回环境。[Role 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/roles/role.py)

`Action` 是具体能力单元，负责封装提示词、模型调用和结构化输出；`Message` 同时携带自然语言和 `instruct_content`，并用 `cause_by / sent_from / send_to` 描述事件来源和路由目标。[Action 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/actions/action.py) [Message 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/schema.py)

`Environment` 本质上是进程内消息总线和协作空间。它按地址把消息放入 Role 的私有缓冲，并在一次环境运行中用 `asyncio.gather` 并发执行所有非空闲 Role。这个并发是**同一 Python 进程中的协程并发**，不是拥有独立文件系统和故障域的 Worker 集群。[Environment 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/environment/base_env.py)

`Team` 负责雇佣角色、设置模型调用预算、发布用户需求、按 `n_round` 推进环境，以及结束时归档仓库。其停止条件主要是团队空闲、轮次耗尽或预算耗尽。[Team 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/team.py)

### 2.2 当前软件公司入口：团队规模是配置出来的，不是推导出来的

当前 `software_company.py` 的默认入口直接创建 `TeamLeader`、`ProductManager`、`Architect`、`Engineer2`、`DataAnalyst`。虽然 Role 可以在运行时设置 Action，TeamLeader 也能把任务发给不同角色，但入口并没有根据仓库规模、变更范围或模块耦合计算“需要多少个 Agent、采用何种拓扑”。[软件公司入口](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/software_company.py)

当前默认 `Team(use_mgx=True)` 使用 `MGXEnv`。普通角色消息先交给 TeamLeader，再由 TeamLeader 选择转发对象，形成近似中心化 Supervisor 的通信结构；它比早期完全固定流水线更动态，但仍然是在预先雇佣的角色集合中路由。[MGXEnv 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/environment/mgx/mgx_env.py) [TeamLeader 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/roles/di/team_leader.py)

### 2.3 MetaGPT 如何读取并修改已有仓库

MetaGPT 确实有增量开发能力，并非只能从零生成项目：

- CLI 中存在 `inc` 和 `project_path`，用于在旧项目上完成增量需求。
- `ImportRepo` 可以克隆 Git 仓库，猜测源码目录，从 README 提取原始需求，并重建类图、调用序列图和文件清单。
- `ProjectRepo` 把源码、PRD、系统设计、任务、代码总结、测试等组织为多个文件仓库。
- 旧版 `Engineer` 在增量模式下先生成 `CodePlanAndChange`，再把旧代码、设计、任务和变更计划放进上下文，通常以“一个 Action 写一个完整文件”的方式更新源码。

对应源码见 [ImportRepo](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/actions/import_repo.py)、[ProjectRepo](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/utils/project_repo.py)、[Engineer](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/roles/engineer.py) 和 [增量变更 Action](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/actions/write_code_plan_and_change_an.py)。

其仓库解析能力有明确边界：`RepoParser.generate_symbols()` 的实际匹配扩展名是 `*.py`，使用 Python `ast.parse` 提取类、函数和全局变量。`ImportRepo` 中对源码根目录的猜测也明显依赖 `__init__.py`。因此，现有逆向工程链路对 Python 项目最自然，不能把源码注释里“py/js”当成已完成的通用多语言语义索引。[RepoParser 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/repo_parser.py)

### 2.4 MetaGPT 的状态、记忆和恢复

基础 `Memory` 是内存中的 `Message` 列表，并按 `cause_by` 建简单索引；Role 有私有消息缓冲、普通记忆和工作记忆。Team、Context、Role 等对象支持 JSON 序列化与恢复。这足以支持 Demo 级重启恢复和对话追踪，但它不是严格的事件溯源数据库，也没有天然提供跨 Worker 的事务、租约、幂等任务和资源锁。[Memory 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/memory/memory.py)

### 2.5 MetaGPT 的代码执行与隔离边界

`Engineer2` 通过 Editor 和 Terminal 在当前工作目录操作文件、运行命令；默认工具映射允许执行终端命令和直接写文件。旧 `RunCode` 路径还包含 `exec()`、`subprocess.Popen()` 和自动 `pip install -r requirements.txt`。这些能力适合受信任的本地实验，但不是我们处理任意外部仓库时应接受的安全边界。[Engineer2 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/roles/di/engineer2.py) [RunCode 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/actions/run_code.py)

MetaGPT 的 Git 封装支持查看变更、新建分支、提交和归档，但默认 `Environment.archive()` 面向当前项目仓库，不提供“每个编码 Agent 一个独立 worktree、统一集成器按补丁合并”的并行写入协议。[GitRepository 源码](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/utils/git_repository.py)

### 2.6 对 MetaGPT 的结论

| 能力 | 评价 | 对我们的处理 |
|---|---|---|
| Role / Action 分离 | 好，职责清楚 | 保留思想，不必继承类层次 |
| 结构化 Message | 好，优于纯聊天 | 升级为强类型事件与产物引用 |
| SOP 与角色订阅 | 好，适合表达协作规则 | 转换成显式任务 DAG |
| 旧仓库增量模式 | 已有，但偏文档转换和文件重写 | 改为检索、影响分析、补丁优先 |
| TeamLeader 路由 | 有动态性，但角色池预设 | 升级为先组队、再执行的 TeamPlan |
| 轮次调度 | 对 Demo 简单有效 | 不适合长任务、恢复和资源冲突 |
| 同进程协程并发 | 对消息处理足够 | 写代码 Worker 必须进程/工作区隔离 |
| 执行安全 | 不足以处理不可信仓库 | 容器、网络/密钥策略、人工门禁必须重做 |

**结论：MetaGPT 是“协作协议参考实现”，不是我们的完整执行底座。**

## 3. 其他 GitHub 项目给出的底层启示

### 3.1 OpenHands Software Agent SDK：生产级 Agent 执行内核参考

[OpenHands Software Agent SDK](https://github.com/OpenHands/software-agent-sdk) 把 Agent 设计为近似无状态配置，把运行状态放入 Conversation 和事件流；底层明确区分 Agent、Tool、Event、Conversation、Workspace 和 Security。Workspace 可以是本地目录，也可以是 Docker、Kubernetes/远程 Agent Server 上的临时环境。它还提供工具执行前的风险分析与确认策略，以及子 Agent 的预算和迭代限制。[OpenHands Agent 架构](https://docs.openhands.dev/sdk/arch/agent) [Workspace 架构](https://docs.openhands.dev/sdk/arch/workspace)

对我们的启示：**Agent 的“思考配置”应与会话状态、执行环境分离；安全确认应是运行时机制，而不是提示词要求。** 第一版可以直接采用 OpenHands SDK 作为 Worker 适配器，也可以仿照其接口写更小的内核，但没有必要重造完整终端、事件和安全体系。

### 3.2 mini-SWE-agent：单 Agent 内核应保持简单

[mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent) 的 `DefaultAgent` 核心就是线性消息历史上的 `query → execute_actions` 循环，并显式限制步骤数、成本和墙钟时间；环境接口可在本地命令、Docker、Bubblewrap、SWE-ReX 等实现间切换。它证明了软件工程能力主要来自模型、仓库环境和反馈闭环，不来自庞大的 Agent 类层次。

对我们的启示：**不要把每个 Worker 做成一个小型 MetaGPT。** Worker 只需要模型、最小工具、任务上下文、限制和轨迹。多 Agent 的复杂度集中在控制平面，而不是复制到每个执行循环。

### 3.3 Agentless：先定位、再修复、后验证是强基线

[Agentless](https://github.com/OpenAutoCoder/Agentless) 使用三阶段流程：分层定位到文件/类/函数/行，采样候选补丁，再运行回归和复现测试重排补丁。它不是多 Agent，却是我们必须超越的基线。

对我们的启示：**多 Agent 不能替代定位和验证。** 如果单条确定性流水线已能解决任务，就不应为了“多 Agent”强行增加沟通成本。

### 3.4 HyperAgent：角色分工应围绕软件工程动作

[HyperAgent](https://github.com/FSoft-AI4Code/HyperAgent) 采用固定的 Planner、Navigator、Code Editor、Executor 四角色，代码导航结合 Zoekt 和 universal-ctags。它比“产品经理—架构师—程序员”的公司模拟更贴近仓库维护。

对我们的启示：角色池应优先按**定位、规划、实现、测试、集成、审查**定义，而不是照搬组织职位。

### 3.5 MaAS、DyLAN、AFlow：动态网络可研究，但不宜直接做 MVP 控制器

[DyLAN](https://github.com/SALT-NLP/DyLAN) 会针对查询执行推理时 Agent 选择、动态多轮交互和提前停止，并使用 Agent Importance Score 做团队优化；它的实验主要是 MATH、MMLU、HumanEval。[MaAS](https://github.com/bingreeky/MaAS) 使用控制器从概率化 Agent supernet 中为不同领域和难度的问题采样子网络，并根据环境反馈优化分布和算子；公开实现同样围绕 GSM8K、MATH、HumanEval等基准。[AFlow](https://github.com/FoundationAgents/AFlow) 则通过 LLM 和搜索，在由 Generate、Review、Revise、Ensemble、Test、Programmer 等算子构成的代码工作流空间中离线迭代优化。

这些方法证明“任务不同，应选不同工作流”具有研究依据，但不能直接证明其控制器能在真实旧仓库中可靠判断变更影响。真实仓库任务还包含文件锁、补丁冲突、构建环境和回归风险；并且在线搜索任意拓扑会产生较高成本和不可控性。

对我们的启示：**MVP 使用有边界的模板选择；学习型路由只在积累带标签的任务轨迹后加入。**

### 3.6 Agent Orchestrator：多 Agent 写代码必须隔离

[Agent Orchestrator](https://github.com/Untrivial-ai/agent-orchestrator) 把每个编码会话放在独立 Git worktree 中，并将 CI 失败、评审意见和合并冲突反馈给对应 Worker。它不负责基于仓库影响动态决定团队，但很好地展示了多 Agent 编码系统的执行控制面。

对我们的启示：**并行 Agent 不能共享同一个可写工作目录。** Worktree、分支、会话状态和反馈路由都应该是一等对象。

## 4. 我们系统的底层方案

### 4.1 总体原则：控制平面与执行平面分离

```text
用户需求 + Git Commit
        │
        ▼
┌──────────────────────────────────────────────┐
│ 控制平面 Control Plane                      │
│ Intake → RepoProfile → ChangeImpact         │
│        → TeamBuilder → Task DAG             │
│        → Scheduler → Gate / Recovery         │
└───────────────┬──────────────────────────────┘
                │ TeamPlan + TaskContract
       ┌────────┼──────────────┐
       ▼        ▼              ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│ Worker A │ │ Worker B │ │ Reviewer │  Agent Runtime
└────┬─────┘ └────┬─────┘ └────┬─────┘
     │             │             │
┌────▼─────┐ ┌────▼─────┐ ┌────▼─────┐
│Worktree A│ │Worktree B│ │只读快照/ │  Execution Plane
│+Container│ │+Container│ │集成分支   │
└────┬─────┘ └────┬─────┘ └────┬─────┘
     └──── Patch ──┴──── Patch ──┘
                    │
                    ▼
          Integrator → Tests → Final Patch
```

控制平面只管理状态、依赖、资源和决策，不直接编辑代码；执行平面只执行带权限和输入边界的任务。这样可以让调度器失败时恢复，也能在不更换控制逻辑的情况下切换 mini-SWE-agent、OpenHands 或自定义 Worker。

### 4.2 建议技术栈

| 模块 | MVP 选择 | 选择原因 | 后续替换点 |
|---|---|---|---|
| 语言 | Python 3.12 | Agent/分析生态完整，便于秋招展示 | 无需多语言控制面 |
| API/CLI | Typer + FastAPI | CLI 先行，后续可接 UI | UI 不进入首版关键路径 |
| 数据模型 | Pydantic v2 | 强类型 Agent 协议和校验 | 保持 JSON 可序列化 |
| 工作流 | LangGraph + SQLite checkpointer | DAG、并行节点、暂停恢复、人工中断 | 后续可换 Postgres/队列 |
| Worker | OpenHands SDK（主实现）+ mini-SWE 风格基线 | 复用事件、Workspace、安全和限制能力，同时保留简单对照组 | 统一 `WorkerAdapter` 接口 |
| 代码检索 | ripgrep + Python AST + import graph | 简单可解释，先支持 Python | 后续加入 tree-sitter/LSP/Zoekt |
| 隔离 | Git worktree + Docker | 文件隔离、补丁化、可回收 | 后续远程容器/K8s |
| 测试 | pytest + Ruff + 项目原生命令 | 有确定性反馈 | 再扩展类型检查/安全扫描 |
| 观测 | JSONL 事件 + OpenTelemetry 可选 | 可回放、可算成本和时延 | 后续接专用平台 |

LangGraph 的价值不在“帮我们写 Agent”，而在持久化图状态、故障恢复、并行子图和人工中断。其 checkpointer 会在步骤间保存状态，并支持从失败 super-step 恢复；中断时可以保存状态，等待人工批准后继续。[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence) [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

**MVP 的明确选型是：OpenHands SDK 承担单 Worker 的模型—工具—事件循环，我们自己实现 LangGraph 控制平面、仓库影响分析和 worktree 调度。** 不使用 OpenHands 的多 Agent 编排来替代核心亮点；另写一个 mini-SWE 风格的最小 `WorkerAdapter` 作为可解释基线和故障回退。这样既不重造执行安全轮子，也不会把动态组队创新锁在某个 SDK 内。

### 4.3 核心领域模型

底层协议不直接传递大段聊天，而传递以下强类型对象：

```python
class RepoProfile(BaseModel):
    commit_sha: str
    languages: dict[str, int]
    modules: list[ModuleInfo]
    dependency_edges: list[DependencyEdge]
    test_commands: list[str]
    baseline_status: BaselineStatus

class ChangeImpact(BaseModel):
    task_type: Literal["bug", "feature", "refactor", "migration"]
    candidate_symbols: list[SymbolRef]
    affected_modules: list[str]
    risk_flags: set[str]
    parallelizable_groups: list[list[str]]
    confidence: float
    evidence: list[EvidenceRef]

class TeamPlan(BaseModel):
    topology: Literal["solo", "pipeline", "fanout", "hierarchical"]
    agents: list[AgentSpec]
    tasks: list[TaskContract]
    edges: list[TaskDependency]
    budget: Budget
    rationale: list[str]

class PatchArtifact(BaseModel):
    task_id: str
    base_commit: str
    diff: str
    touched_files: list[str]
    tests_run: list[TestResult]
    assumptions: list[str]
```

`evidence` 必须引用真实文件、符号、搜索结果或测试输出。LLM 可以提出推断，但不能在没有证据时直接扩大影响范围。

### 4.4 先读后改：旧仓库理解链路

“读仓库”不能等价于把所有源码塞进上下文。建议按以下顺序生成可缓存的 `RepoProfile`：

1. 固定基线 commit，检查工作树状态，不在用户当前分支直接写入。
2. 读取仓库说明和约束文件：README、贡献指南、Agent 指令、构建文件、CI、依赖清单。
3. 枚举语言、模块、测试目录、入口和构建命令。
4. 对 Python 使用 AST 建符号表和 import graph；用 ripgrep 建词法反向索引。
5. 运行只读/基线验证，记录哪些测试在修改前已经失败。
6. 将用户需求拆为实体、行为、错误信息、接口、约束等检索线索。
7. 结合词法命中、符号引用、依赖邻居和测试关联，生成候选影响集合。
8. Navigator Agent 只对候选集合做语义复核，输出 `ChangeImpact` 和证据。

第一版只支持 Python 仓库是合理边界。多语言能力应通过 `LanguageAdapter` 扩展，而不是让 LLM 自称理解所有语言：

```text
LanguageAdapter
 ├─ PythonAdapter(AST, import graph, pytest)
 ├─ JavaAdapter(tree-sitter/LSP, Maven/Gradle)   # 后续
 └─ TypeScriptAdapter(tsserver, npm scripts)     # 后续
```

### 4.5 动态组队：由影响范围决定，而不是由 LOC 决定

代码行数只作为成本先验，不能作为主要路由特征。动态调度使用以下可解释特征：

- 预计影响的模块、文件和符号数量；
- 依赖图扇出、跨模块边数量、循环依赖和核心模块中心性；
- 是否跨 API、服务、数据层、前端或基础设施；
- 是否涉及认证、权限、支付、数据迁移、并发、公开 API；
- 候选任务能否形成文件集合不相交的并行组；
- 测试覆盖、基线健康度和复现测试是否存在；
- 定位置信度、需求歧义、成本和时间预算。

建议先计算解释性分数，而不是让 LLM直接给 Agent 人数：

```text
risk = 2*高风险标记 + 跨层数 + 依赖扇出分档 + 基线失败标记
scope = 影响模块数 + 影响文件数分档 + 新增接口数
uncertainty = 定位低置信度 + 需求歧义 + 无复现测试
parallelism = 文件不相交任务组数 - 高耦合惩罚
```

规则路由示例：

| 条件 | 拓扑 | Agent |
|---|---|---|
| `scope` 小、`risk` 低、定位清楚 | `solo` | 1 个 Coding Worker，调度器执行机械测试 |
| 单模块但需要独立复核 | `pipeline` | Navigator → Developer → Reviewer |
| 至少两个文件集合不相交的任务组 | `fanout` | Planner → N 个 Module Worker → Integrator → Tester |
| 高风险、跨层或低置信度 | `hierarchical` | Navigator/Architect → 专项 Worker → Integrator → Reviewer，含人工门禁 |

**动态 Agent 数量由任务节点数量产生，不由仓库总 LOC 直接映射。** 首版建议并行写 Worker 上限为 3，总 Agent 上限为 6，避免 Token 与冲突成本失控。

### 4.6 协作关系：有限模板可以运行时实例化

模板不是固定团队。每次任务先生成 `TeamPlan`，再实例化需要的角色和任务节点：

```text
solo:
  Developer → Gate

pipeline:
  Navigator → Developer → Reviewer → Gate

fanout:
                    ┌→ Worker(module A) ─┐
  Planner/Splitter ─┼→ Worker(module B) ─┼→ Integrator → Gate
                    └→ Worker(module C) ─┘

hierarchical:
  Navigator → Architect → Specialist Workers → Integrator
                         ↘ Security/DB Reviewer ↗
                                      ↓
                                Human Approval → Gate
```

Agent 之间默认不自由群聊。通信通过控制平面中的 `TaskContract`、`ArtifactRef` 和反馈事件完成。只有 Integrator 能把 Worker 补丁应用到集成分支；只有 Scheduler 能创建新任务或扩缩团队。

### 4.7 并行写入、冲突和回滚

每个写任务都遵守以下协议：

1. 从同一 `base_commit` 创建独立 worktree 和临时分支。
2. TaskContract 声明允许修改的文件/模块集合；越界写入触发失败或重新规划。
3. Worker 在容器中编辑并运行局部测试，只返回 `PatchArtifact`。
4. Integrator 按依赖顺序将补丁应用到集成 worktree。
5. 文本冲突不交给多个 Worker 继续互改；创建单独 `ConflictResolutionTask`。
6. 合并后运行影响测试，再运行项目定义的全量门禁。
7. 门禁失败则回滚最近补丁或生成带失败证据的修复任务。
8. 主分支不自动提交；最终产物是可审查 diff、测试报告和 TeamPlan 轨迹。

这比让多个 MetaGPT Role 共享 `project_path` 更容易推理，也能准确记录哪个 Agent 引入了哪个变化。

### 4.8 安全模型：仓库内容是不可信输入

必须同时防范恶意脚本和仓库内 prompt injection。安全不能只靠系统提示词：

- 默认在容器中运行；限制 CPU、内存、进程数、磁盘和执行时间。
- 默认关闭网络；依赖安装进入单独、可审批阶段，使用允许列表和缓存。
- 不把宿主机密钥、SSH Agent、云凭证挂进 Worker 容器。
- 仓库文本只作为数据，不能改变系统工具权限和 TeamPlan。
- 终端工具使用参数化接口；危险命令、越权路径和网络请求进入确认策略。
- Worker 只能写自己的 worktree，不能写主仓库、其他 worktree 或控制数据库。
- 数据库迁移、认证、权限、依赖供应链变更必须人工审批。
- 保存工具调用、diff、测试和审批事件，支持完整回放。

|---|---|---|---|
| 目标 | 从需求模拟软件公司并产出项目 | 在真实旧仓库上完成可验证更新 | 场景更聚焦 |

| 并行 | 同进程 Role 协程 | 独立 worktree/容器 Worker | 避免相互覆盖 |

核心改进不是“Agent 更多”，而是以下闭环：

```text
仓库证据 → 影响分析 → 有界动态组队 → 隔离补丁 → 确定性门禁 → 反馈再规划
```

## 6. 可行性分析与主要风险

### 6.1 分层可行性

| 子系统 | 技术可行性 | MVP 难度 | 判断 |
|---|---:|---:|---|
| Python 仓库扫描与符号索引 | 高 | 中 | AST、ripgrep、Git 均成熟 |
| 需求到候选文件定位 | 中高 | 中高 | 可用 Agentless 式分层定位与证据约束 |
| 单 Agent 补丁与测试闭环 | 高 | 中 | mini-SWE/OpenHands 已证明执行模式 |
| 有限模板动态组队 | 高 | 中 | 是分类/规划问题，不需训练控制器 |
| worktree 并行与补丁集成 | 高 | 中高 | Git 机制成熟，需处理文件锁和冲突 |
| 任意动态拓扑搜索 | 中低 | 高 | 数据、成本、稳定性不足，不进 MVP |
| 多语言语义影响分析 | 中 | 很高 | 必须逐语言适配，不应首版承诺 |
| 生产级不可信代码沙箱 | 中 | 很高 | Docker 只是起点，不宣称绝对安全 |

### 6.2 最大技术风险

**风险一：错误拆分导致并行修改相互依赖。** 缓解方式是只有文件/符号写集合明确不相交时才并行；高耦合任务走 pipeline 或 hierarchical。

**风险二：定位错误会让所有下游 Agent 在错误上下文中努力。** 缓解方式是 ChangeImpact 必须携带证据、置信度和候选备选；低置信度自动加入 Navigator/Reviewer，而不是简单增加 Developer。

**风险三：测试通过不代表需求完成。** 缓解方式是先生成需求验收条件和复现测试，再修改代码；Reviewer 同时检查 diff 与验收条件。

**风险四：多 Agent 成本大于收益。** 缓解方式是把 `solo` 作为默认，并将“减少 Agent”视为路由成功；所有实验记录成功率、成本和时延。

**风险五：第三方仓库执行伤害宿主机。** 缓解方式是禁用本地执行作为默认选项、容器无网和无密钥、依赖安装审批、资源限制与工作区路径校验。

### 6.3 项目边界

首版明确不做：

- 不支持任意编程语言，先只支持 Python；
- 不做从需求到完整大型产品的从零生成；
- 不让多个 Worker 写同一个 worktree；
- 不在线训练或搜索任意 Agent 图；
- 不自动 push、merge 到用户主分支；
- 不宣称能安全执行所有恶意仓库；
- 不以 Web UI、向量数据库或 Kubernetes 作为首版亮点。

有这些边界，项目作为个人秋招项目是可行的；去掉这些边界，就会迅速变成生产平台工程，超出合理范围。

## 7. 编码前必须通过的三个技术尖峰

### Spike A：单 Agent 旧仓库更新闭环

选取一个中小型 Python 仓库和 5 个真实/自造 Issue，实现：

```text
固定 commit → 建索引 → 定位文件/符号 → 生成补丁
→ Docker 中运行复现测试和回归测试 → 输出可审查 diff
```

通过标准：

- 5 个任务中至少 4 个能正确定位到包含金补丁修改点的文件集合；
- 至少 3 个任务完成测试通过的有效补丁；
- 所有写入只发生在临时 worktree；
- 每次运行保存完整证据、命令、成本和 diff。

### Spike B：双 Worker 并行与集成

准备一个可拆成两个不相交模块的需求：

- Scheduler 生成两个 TaskContract；
- 创建两个独立 worktree 和容器；
- 两个 Worker 并行产生补丁；
- Integrator 在第三个 worktree 中按顺序应用；
- 执行集成测试；
- 再准备一个故意重叠文件的反例，系统必须拒绝并行或生成冲突任务。

通过标准：没有共享目录覆盖；补丁可追溯；无冲突任务可自动集成；重叠任务不会静默覆盖。

### Spike C：动态路由是否真的有收益

准备至少 12 个任务，覆盖简单单文件、单模块、多模块可并行、高风险/低置信度四类。比较：

1. 单 Agent；
2. 固定 4 Agent；
3. 自适应模板路由。

通过标准不是“自适应组赢所有任务”，而是满足以下任一组合：

- 在成功率不下降超过 5 个百分点的前提下，平均成本或时延降低至少 20%；或
- 在成本增加不超过 30% 的前提下，多模块任务成功率提高至少 15 个百分点；
- 路由器能在至少 80% 的简单任务中选择 `solo` 或最小 pipeline。

这些阈值是项目内部的 Go/No-Go 工程门槛，不是已有论文结论。若失败，应先修正影响特征和拓扑模板，而不是继续增加 Agent。

## 8. 正式实现路线

### 阶段 0：冻结问题定义

- 输入：本地 Git 仓库、基线 commit、自然语言需求；
- 输出：patch、测试报告、TeamPlan、运行轨迹；
- 支持：Python bug fix 和小型 feature；
- 非目标：自动合并到主分支、通用多语言、从零生成整套产品。

### 阶段 1：Repository Intelligence

- Git 快照与基线检查；
- 文件/语言/模块统计；
- Python 符号表、import graph、测试发现；
- 需求检索和 `ChangeImpact`；
- 为结果建立缓存键：`commit_sha + analyzer_version`。

### 阶段 2：可靠的单 Worker

- `WorkerAdapter` 接口；
- Shell/File/Patch/Test 最小工具；
- DockerWorkspace；
- 步骤、成本、时间限制；
- PatchArtifact 和运行轨迹。

### 阶段 3：控制平面

- LangGraph 状态图；
- SQLite checkpointer；
- TeamBuilder 规则与四种拓扑；
- TaskContract、依赖、重试和人工中断；
- 资源锁与文件写集合校验。

### 阶段 4：并行和集成

- worktree 生命周期管理；
- fanout 并行执行；
- Integrator 和冲突任务；
- 局部测试、影响测试、全量门禁；
- 最终报告和可回放事件。

### 阶段 5：评测与学习型路由（可选）

- 对照单 Agent、固定多 Agent、自适应系统；
- 分析每类任务的收益与失败模式；
- 只有积累足够轨迹后，才尝试分类器、bandit 或 MaAS 式控制器；
- 保留规则路由作为安全回退。

## 9. 评测设计

### 9.1 主要指标

| 指标 | 定义 |
|---|---|
| Resolution Rate | 修改后新增/隐藏测试全部通过的任务比例 |
| Regression Rate | 原本通过的测试在补丁后失败的比例 |
| Localization Recall | 金补丁涉及文件是否落入候选集合 |
| Patch Scope | 无关修改文件数、diff 行数 |
| Cost | LLM 调用成本或输入/输出 Token |
| Latency | 从需求到最终结果的墙钟时间 |
| Coordination Overhead | Agent 消息、返工、冲突和集成失败次数 |
| Agent Efficiency | 每成功任务使用的 Agent 数与调用数 |

### 9.2 实验集合

第一版建议使用两类数据：

- 公开基准的 Python 子集，例如 SWE-bench Verified/Lite 中可本地复现的任务；
- 3～5 个中小型 Python 开源仓库中的 20～30 个自建更新任务，包含单文件、多模块、可并行和高风险任务。

公开基准用于可比较性，自建集用于验证“动态拓扑”——因为 SWE-bench 中大量任务并不天然需要多 Agent。

### 9.3 必须做的消融实验

- 去掉依赖图，只用 LOC 和关键词路由；
- 去掉动态路由，固定四 Agent；
- 去掉 Reviewer；
- 去掉 worktree 隔离，仅串行执行；
- 规则路由与 LLM 直接路由对比。

如果“只用 LOC”与完整影响特征没有明显差异，说明仓库分析没有贡献；如果固定多 Agent 与动态系统相当，说明第二个亮点尚未成立。

## 10. 最终决策

### 10.1 推荐方案

**推荐从零实现一个小型控制平面，不 fork MetaGPT 主体。**

- 借鉴 MetaGPT：Role/Action 分离、结构化 Message、SOP、预算、结构化中间产物；
- 借鉴 mini-SWE-agent/OpenHands：简单 Worker 循环、Workspace 抽象、事件、限制和安全确认；
- 借鉴 Agentless/HyperAgent：分层定位、Navigator/Editor/Executor 角色；
- 借鉴 Agent Orchestrator：worktree 隔离和反馈路由；
- 借鉴 MaAS/DyLAN/AFlow：把动态团队视为可优化策略，但推迟到有数据之后。

### 10.2 何时可以开始完整编码

只有满足以下条件才开始完整系统：

- Spike A 证明旧仓库补丁闭环有效；
- Spike B 证明 worktree 并行与集成可靠；
- Spike C 证明动态路由至少在成本、时延或成功率之一有可测收益；
- 已冻结 Python-only、patch-only、no-auto-merge 的 MVP 边界；
- OpenHands `WorkerAdapter` 已通过 Spike A；若其依赖或行为无法满足要求，则已用同一接口验证 mini-SWE 风格回退实现。

在此之前，合理的下一步不是搭 UI 或写很多角色，而是先实现 Spike A 的最小实验仓库和评测脚本。

### 10.3 一句话架构定位

> 一个以代码变更影响图为依据、用持久化任务 DAG 动态组织 Agent、在隔离 Git worktree 中生成补丁并以确定性测试门禁收敛的软件演进控制系统。

---

## 11. 限制与仍需回答的问题

1. **主 Worker 选型仍需 Spike A 验证，而不是继续讨论。** 默认采用 OpenHands SDK；若依赖重量、版本变化或工具行为影响复现，就通过 `WorkerAdapter` 切换到 mini-SWE 风格回退实现。回退实现更透明，但必须补齐安全与事件能力。
2. **动态路由没有现成真实仓库训练集。** 第一版只能把它视为规则系统和待验证假设，不能宣称“智能最优组队”。
3. **测试质量决定上限。** 缺少可复现测试时，系统只能提供补丁候选，不能证明需求已正确完成。
4. **Docker 不是绝对安全边界。** 对恶意仓库的生产级隔离还需要更严格的容器配置、微虚拟机或远程一次性环境。
5. **跨语言影响分析是独立工程。** Python MVP 成功后，应逐语言增加 Adapter 和评测，而不是依赖通用提示词。
