# EvoWeave 秋招演示与答辩指南

## 1. 推荐叙事

先讲问题，再讲多 Agent：现有代码更新任务的难点不是“让多个模型聊天”，而是固定版本代码理解、任务边界、并发价值、上下文隔离、补丁冲突和确定性验收。EvoWeave 的选择是保留一个总调度器，按证据创建无固定角色的临时 Agent，并让代码约束而不是提示词承担安全边界。

一句话介绍：

> EvoWeave 面向已有 Python 仓库，根据需求、代码规模、依赖、风险和输入模态动态生成任务 DAG，为每个节点装配通用 Agent，并在独立 worktree 中产出经过确定性门禁验证的补丁。

## 2. 十分钟演示流程

1. 用 `benchmark validate` 展示 12 个任务、固定 commit 和图片哈希没有漂移；
2. 用 `benchmark audit` 展示简单任务、并行任务、串行任务和图片负例的不同拓扑；
3. 运行单文件 fixture，展示只创建一个实例和低档模型需求；
4. 运行多模块 fixture，展示两个就绪任务真并发或按 import 关系串行；
5. 展示首选模型失败后新 Agent、新规格和新版路由，而不是原地静默切换；
6. 展示最终 diff、真实测试命令、退出码和主工作树未被修改；
7. 展示隐藏验收双向自洽测试和一次真实运行证据，最后主动说明正式 108 条效果矩阵和 Docker 实机隔离尚未完成。

## 3. 建议准备的五个场景

| 场景 | 应展示的证据 | 关键结论 |
|---|---|---|
| 单文件修复 | 1 个 TaskSpec、1 个 Agent、最终补丁 | 简单任务不滥用多 Agent |
| 多模块并行 | 两个首轮模型调用时间重叠、写集合不重叠 | 多 Agent 用于可并行工作，不是用于凑角色 |
| 串行依赖 | pricing → service 的 DAG | 关系来自代码依赖 |
| 图片负例 | 输入存在图片，但 `image_agent_count=0` | 多模态按需分配 |
| 模型回退 | Agent/Spec/Route 版本同时变化 | 回退可追溯且不覆盖历史 |

高风险场景可作为安全加分项：支付、权限、安全和迁移需求在任何模型网络调用前暂停，只有显式批准后继续。

## 4. 面试常见追问

### 为什么不用 MetaGPT 的固定角色？

固定角色适合重复的软件公司流程，但既有仓库更新的实际工作量并不稳定。一个单文件修复不需要产品经理、架构师、开发和测试同时参与；跨模块任务也可能需要两个并行实现实例，而不是一套固定职位。EvoWeave 将能力、权限、模型和任务边界放入运行时规格，同一 Runtime 可以形成不同功能。

### 总调度会不会被所有 Agent 的上下文污染？

总调度只读取 L3 控制视图：任务状态、结构化摘要、风险、证据和产物引用。源码、完整日志、图片和工具轨迹留在 L1/L2。最终要通过指标比较总调度上下文与 Worker 上下文，当前已经有计量协议，完整真实模型数据仍待采集。

### 动态创建更多 Agent 一定更好吗？

不是。Agent 数由可独立执行范围和依赖决定，模型档位由难度和模态决定。当前 12 任务规划审计中，动态策略平均 1.33 个 Agent，简单任务只创建一个；这说明策略具备“少创建”的能力，但效果优越性仍需真实对照实验验证。

### 如何防止 Agent 越权？

每个任务绑定固定 commit、读写范围和工具白名单；写入发生在独立 worktree。补丁还要经过 SHA、base commit、实际路径、敏感文件和冲突检查。最终通过由真实 Pytest/Ruff 命令决定，模型自述不能绕过。

### 三家模型如何选择？

先按当前账号实测可用性、输入模态、上下文、工具调用和结构化输出能力硬过滤，再按任务难度选择档位并稳定排序。价格不进入路由。图片只发送给相关任务；失败时创建新版本路由和新 Agent。

## 5. 可以说与不能说

可以说：

- 阶段 6 的完整离线端到端闭环已通过自动化测试；
- 规划审计使用固定 Git commit 和真实仓库画像，不是手写拓扑；
- 系统已具备三种 Agent/模型策略的强类型对照、隐藏验收、真实运行器和缺失数据保护；
- API 网关、模型诊断和回退链已经实现。

暂时不能说：

- 动态方案已经在真实模型上显著优于基线；
- 12 × 3 × 3 实验已经完成；
- Docker 隔离已经在本机真实验证；
- 任意语言、任意大型仓库或恶意仓库都能安全更新；
- 模型调用被强制终止后可以逐 Token 无重复恢复。

主动讲清边界会让项目更可信，也能把后续工作自然落到正式真实模型矩阵、Docker 实测和恢复加固上。
